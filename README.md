# personal-platform-frontend

Frontend таскменеджера на Next.js, React і TypeScript.

## Локальний запуск

1. Встановіть залежності: `npm install`.
2. Скопіюйте `.env.example` у `.env.local`. За замовчуванням `NEXT_PUBLIC_API_URL=http://localhost:4000/api`.
3. Запустіть backend. Його CORS має дозволяти адресу frontend (локально `http://localhost:3000`).
4. Запустіть `npm run dev` та відкрийте `http://localhost:3000`.

Після зміни `NEXT_PUBLIC_API_URL` перезапустіть dev-сервер; для production виконайте нову збірку, оскільки Next.js вбудовує публічні змінні у клієнтський код.

## API

- `GET /tasks` — масив повних Task DTO; `GET /tasks?view=today` — підмножина «Сьогодні»; `GET /tasks?archived=true` — архів.
- `GET /tasks/:id`, `POST /tasks`, `PATCH /tasks/:id` — повний Task із `isToday` та nullable `routineOccurrence`, включно з полями ланцюжка виконань.
- POST вимагає назву, дедлайн і тривалість або початкові підзадачі. PATCH передає лише змінені поля; контекст не входить у body.
- `DELETE /tasks/:id` — видалення задачі.

Список, деталі, POST і PATCH отримують `timezone`, `overdueMode`, `overdueDays` із завантажених налаштувань. Історія, DELETE і маршрути підзадач цих параметрів не отримують. Після запису підзадачі окремий GET батька використовує актуальний контекст; повтор після помилки GET не повторює запис. Повний Task із POST/PATCH оновлює список без додаткового GET, якщо контекст не змінився.

URL: `/` — поточні, `/?view=today` — сьогодні, `/?archived=true` — архів. Архів має пріоритет над view; інші view означають поточні. Переходи зберігають фільтри й сторонні query-параметри; «Скинути» зберігає розділ. Фільтри, пошук, сортування та зміна теми не завантажують задачі повторно.

«Сьогодні» використовує тільки backend isToday. Після фільтрації задачі поділяються на «До виконання» та «Виконано сьогодні» (DONE), зі збереженням сортування всередині кожної групи. Обидві групи входять до загального лічильника. Повний Task DTO містить `completedAt: string | null` — підтверджений backend момент поточного завершення; frontend його не обчислює. Завершення й повторне відкриття переміщують ту саму картку між групами, якщо isToday залишається true; розгортання підзадач зберігається. Поточні задачі й архів залишаються одним списком.

Для визначення timezone майбутніх occurrence кожне завантаження «Сьогодні» паралельно читає поточний список. Один таймер раз на п’ять хвилин перевіряє календарні дати користувача й occurrence з цього списку. GET виконується лише після зміни цих дат, зокрема при поверненні у вкладку; є також кнопка «Оновити список». Вчорашні завершення зникають за новою відповіддю backend. Зміна API-контексту відразу приховує попередній результат; власники відкритих форм тимчасово зберігаються з явним повідомленням про неактуальні картки. Новий контекст після успішного запису оновлюється читанням, без повтору мутації.

Перевірки: `npm run lint`, `npm run typecheck`, `npm run build`.

## Компонування списку задач

Підсумок над фільтрами рахує весь завантажений список поточного розділу: TODO, IN_PROGRESS, неактивні (CANCELED/PAUSED/POSTPONED) та DONE. Він не залежить від пошуку, фільтрів і підзадач та не виконує API-запитів. Розкладка неактивних доступна через клавіатурне розкриття. Під час завантаження або помилки без даних замість достовірних нулів показується повідомлення.

На широкому екрані заввишки від 48rem каркас задач займає viewport, панель керування залишається над областю прокручування, обидві групи «Сьогодні» прокручуються разом. Навігація має власне прокручування, якщо не вміщається. Для вузьких/низьких viewport використовується звичайне прокручування документа, а на мобільному фільтри можна розгорнути кнопкою з кількістю активних умов. Згортання не змінює URL. `/settings` зберігає звичайне компонування.

## Особисті налаштування

Екран `/settings` доступний із меню. Налаштування застосовуються після натискання «Зберегти», без облікового запису. Адаптер `settings-storage.ts` зберігає перевірені поля та `version: 1` у ключі `personal-platform.settings`. Якщо localStorage недоступний, provider зберігає зміни лише в пам’яті поточної вкладки. Події `storage` оновлюють інші вкладки без повторного запису; незбережена форма пропонує завантажити зовнішні значення або зберегти власні.

Часовий пояс за замовчуванням береться з браузера, резервний — UTC. Відображення дат використовує обраний пояс. Відкрита форма фіксує його до закриття, щоб зовнішня зміна налаштувань не переосмислила чернетку. Спільні helpers на `@js-temporal/polyfill` відхиляють неіснуючі години DST та вимагають явного вибору UTC-зсуву для повторених годин. API отримує UTC; незмінені дати не включаються в PATCH (для перенесення зберігається точне початкове `plannedAt`).

Теми використовують спільні CSS-змінні. Системна тема реагує на `prefers-color-scheme`; збережена світла або темна палітра встановлюється блокувальним скриптом у head до відображення сторінки. Він змінює CSSOM, зберігаючи DOM однаковим для SSR і hydration.

Параметри прострочення застосовуються до перегляду «Сьогодні» на backend: limited додає N попередніх календарних днів, none залишає тільки сьогодні, all додає всі попередні дні. Локальні дати й час occurrence відображаються у його календарі, окремо від особистого планування та дедлайну. Беклог поки відсутній.

## Повторювані задачі

`/routines` показує список шаблонів, створення, редагування, деталі, preview розкладу, паузу/відновлення та явну генерацію задач. Видалення у frontend немає. «Активний» означає лише відсутність паузи. Шаблони підзадач мають власний порядок і тривалість; вони не є Task/Subtask та не мають статусів виконання.

Окремі модулі `routine-types.ts`, `routine-validation.ts`, `routine-format.ts`, `routines.ts` підтримують schedule v1 (DAILY, WEEKLY DAYS/WINDOW, MONTHLY DAY/WINDOW/LAST_DAY, AFTER_COMPLETION) та NEVER/UNTIL_DATE/COUNT. Routines не отримують today-контекст: календар і час належать timezone шаблону.

Кнопка «Нове повторення» відкриває модалку з основними полями та редактором шаблонів підзадач ліворуч і розкладом праворуч; на мобільному колонки складаються вертикально. Початкові timezone та дата беруться із завантажених налаштувань і локального сьогодні в цьому поясі. Зміна timezone не переосмислює введену дату. Політика короткого місяця задається явно для DAY/WINDOW; COUNT означає заплановані виконання, а не кількість DONE.

`create-routine-input.ts` перевіряє поля, локальні дати, інтервали й перехресні межі, обрізає пробіли та явно складає одну discriminated-union гілку schedule v1. При підзадачах оцінка показує суму лише для читання; після видалення всіх рядків повертається попередня ручна оцінка. POST надсилає лише назви й числові тривалості підзадач, без локальних ID або статусів. Переповнення суми блокує збереження.

POST `/routines` використовує спільний API-клієнт і runtime-валідацію Routine. Синхронний guard захищає від подвійного submit; під час запиту редагування й закриття заблоковані. Помилки залишають повну чернетку, відомі validation paths прив’язуються до полів. Видалена сфера потребує ручного оновлення довідника/вибору та повторного POST користувачем. Невдале завантаження Areas не блокує створення без сфери. Успішний DTO одразу додається до списку без повторного GET із повідомленням «Шаблон повторення створено». Збереження шаблону не створює задачі автоматично й не запускає generation або preview.

Створення й редагування використовують одну `RoutineFormModal`, спільні поля, валідацію та редактори розкладу/підзадач. Чернетки захищені наявними `DiscardChangesDialog`, `useHistoryTraversalGuard` і стандартним `beforeunload`. Escape/«Скасувати» пропонують відкинути зміни; під час POST/PATCH редагування, закриття й повторний submit заблоковані. Після закриття фокус повертається до кнопки відкриття. Спільна форма Task та її поведінка не змінювалися.

Дія «Редагувати» спершу читає актуальний GET `/routines/:id`; лише після успіху відкривається форма. Завантажений snapshot фіксується до закриття, тому фонові оновлення не перезаписують чернетку. `edit-routine-input.ts` нормалізує текст/числа/порядок weekday selection і порівнює структури без залежності від порядку ключів об’єктів. Без змін PATCH не виконується. Зміна назви не надсилає незмінені schedule/endCondition; очищення сфери передає `areaId: null`. Змінені schedule/endCondition передаються цілком; підзадачі — впорядкованим масивом лише з назв і тривалостей. При видаленні всіх підзадач передаються `subtasks: []` та власна тривалість. Наявний UI підтримує додавання, зміну й видалення рядків; окремих кнопок перестановки не додано.

Чинний Routine DTO не містить достовірної ознаки попередньої генерації. Форма пояснює обмеження, але не вгадує його й не шукає зв’язків через Tasks. Конкретний 409 про заборону календарних змін після генерації отримує окреме пояснення. «Відновити початковий розклад» повертає лише schedule, timezone, startDate та endCondition, зберігаючи інші поля й підзадачі. Повтор PATCH виконує лише користувач; інші 409 залишаються окремими конфліктами. Уже створені задачі не переписуються. Після успішного PATCH список оновлюється повним DTO без обов’язкового GET; попередній запит списку скасовується, щоб не перезаписати результат.

Preview виконує тільки GET з `from`, `to`, `limit=100`: початково сьогодні у timezone Routine та наступні 30 днів. Діапазон обмежений 366 днями включно. Зміна полів не надсилає запиту до натискання кнопки. Локальні дати відображаються без перетворення на timestamps; календар повторень обчислює backend. Невідомі diagnostics/limitations залишаються валідними даними й отримують нейтральне пояснення. AFTER_COMPLETION не надсилає припущень про завершення або номер виконання; preview не є історією чи списком створених задач.

Пауза надсилає лише PATCH `{ paused: boolean }`, блокує повторні записи відповідного шаблону та оновлює список/відкриті деталі повним DTO. Старий preview скидається й повторно читається для останнього застосованого діапазону. Помилка preview після успішної паузи відображається окремо; повторюється лише GET. Уже створені задачі не змінюються. Запізнілі відповіді деталей і preview відкидаються через AbortSignal та перевірку поточного ресурсу.

Ручна перевірка на мокованому API: відкрити всі види розкладу, перевірити вікна й політики короткого місяця; preview з DST/невідомими обмеженнями/truncated/404; паузу й відновлення, повторні натискання та успішний PATCH із невдалим preview; Escape, Tab/Shift+Tab і повернення фокуса. Повторити на 1440/390 px у light/dark та перейти до інших розділів.

Створення на моках: масаж кожні 2 дні до дати, понеділок/четвер, вікно субота–неділя, місячне вікно 15–23, останній день місяця, AFTER_COMPLETION через 90 днів; NEVER/UNTIL_DATE/COUNT. Перевірити перемикання зі збереженням прихованих чернеток, підзадачі/переповнення/повернення ручної оцінки, 400/404 зі збереженням полів, подвійний submit, discard і Back/Forward. У Network має бути один POST на збереження й жодного generation-запиту.

Редагування на моках: без змін — без PATCH; лише назва — лише `title`; очищення сфери; усі розклади/умови завершення; підзадачі та перехід до ручної тривалості. Перевірити спеціальний 409 і відновлення календаря зі збереженням інших правок, окремий concurrency 409, 400/404, повторний submit та запізнілий GET. Повторити створення, preview і pause/resume; на широкому/390 px перевірити прокручування, Tab/Shift+Tab, Escape, discard і обидві теми.

### Явне створення задач із Routine

Картка має дію «Створити задачі» з окремим діалогом підтвердження. Для paused-шаблону кнопка недоступна з поясненням необхідності відновлення. Початковий діапазон — сьогодні та наступні 30 календарних днів у timezone Routine. Локальні дати перевіряються за тим самим контрактом, що й preview: від 0001 до 9999 року, `from <= to`, максимум 366 днів включно. Вікно, яке перетинає діапазон, створюється цілком. Ліміт — 100 нових задач за запит; AFTER_COMPLETION створює максимум одне нове виконання за запуск, а наступника визначає backend за фактичним завершенням.

Тільки явне підтвердження викликає POST `/routines/:id/generate` з body `{ from, to }`. Today-контекст, query, limit, completedAt і номер виконання не передаються. Відкриття діалогу, зміна дат, GET і preview нічого не генерують. Синхронний guard блокує подвійний submit; під час запиту дати, закриття й конфліктні дії заблоковані. Для незбережених дат використані наявні discard-dialog, history guard і beforeunload.

Runtime-валідація перевіряє посилання, лічильники й відповідність діапазону та Routine. Успішний результат лишається у діалозі: created та existing показуються окремо, при 0/0 є порожній стан. Existing не відкриваються автоматично: серед них можуть бути м’яко видалені задачі. Новий запуск завжди потребує нового натискання; зміна дат прибирає попередній успішний результат.

Помилки 400/404/409 зберігають діапазон; пауза, очікування DONE, DST, історія й ліміт мають різні пояснення. Для втрати відповіді, 5xx або невалідної успішної відповіді показується невизначений результат: запит міг виконатися, а повтор за тим самим діапазоном не дублює збережені виконання. Автоматичного повтору POST немає. Якщо після цього змінити дати, попередній запит явно відокремлюється й має дію відновлення його діапазону без надсилання.

Окрема дія «Перейти до поточних задач» відкриває `/`. Після успіху або невизначеного результату `task-list-invalidation.ts` позначає Tasks для повторного GET, включно зі збереженим станом маршруту. Generate-відповідь не вставляється у Tasks вручну: повних DTO в ній немає. Current/today відбір не змінюється. Допоміжний GET після генерації не запускається, тому його помилка не може повторити запис.

Ручна перевірка на моках: відкрити діалог без POST, змінити діапазон, підтвердити подвійним натисканням (один POST), перевірити created/existing/0–0 та нове явне підтвердження. Перевірити paused/AFTER_COMPLETION, 400/404/різні 409, втрату відповіді й явний повтор за збереженим діапазоном. Перейти до Tasks та переконатися в новому GET. Повторити клавіатуру, discard, 390 px, light/dark і наявні дії Routines.

Ручна перевірка: збережіть налаштування й перезавантажте сторінку; відкрийте дві вкладки та створіть конфлікт чернетки; перевірте три теми й клавіатурний діалог відкидання змін. Для Europe/Kyiv введіть `2026-03-29 03:30` (неіснуючий час) і `2026-10-25 03:30` (вибір зсуву). Перевіряйте мутації задач тільки на мокованому API.

Незбережені налаштування захищені під час переходів меню та Back/Forward між записами поточного документа. Кореневий `HistoryTraversalProvider` додає власні мітки до state стандартних `pushState`/`replaceState`, зберігаючи решту state і точний URL. При заблокованому `popstate` форма залишається змонтованою, поточний запис відновлюється, а підтвердження відтворює перший запитаний перехід. Нових записів історії для захисту не додається. За наявності публічного Navigation API використовуються точні ключі записів; інакше — індекси History API.

Обмеження: `popstate` надходить після зміни адреси, тому перед відновленням URL може коротко з’явитися адреса призначення. Для F5, закриття вкладки й переходів між різними документами (зокрема до сторінки перед прямим відкриттям `/settings`) працює стандартний `beforeunload`, а не власний діалог. Його показ залежить від правил браузера та взаємодії користувача зі сторінкою. Невідомі записи історії, створені поза відстеженням поточного документа, не відновлюються навмання.

Для перевірки Back/Forward відкрийте задачі → налаштування → архів, поверніться в налаштування та змініть поле. Перевірте обидва напрямки, «Залишитися» (чернетка, адреса й фокус збережені), «Вийти без збереження» (точний запитаний запис), серію швидких натискань і навігацію після збереження. Кількість записів історії після скасування має залишитися незмінною.
