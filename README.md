# personal-platform-frontend

Frontend таскменеджера на Next.js, React і TypeScript.

## Тимчасовий екран доступу

У локальному `.env.local` задайте власне значення `NEXT_PUBLIC_APP_ACCESS_PASSWORD` і перезапустіть dev-сервер. У `.env.example` значення навмисно порожнє: без налаштованого пароля доступ закритий. Пароль порівнюється точно, включно з пробілами, і після входу зберігається у localStorage (`personal-platform.access-password`). Зміна env робить старе збережене значення непридатним. «Вийти» видаляє значення, зберігає поточний URL і використовує чинне підтвердження незбереженої форми. Вихід або зміна пароля у сховищі іншої вкладки повторно перевіряє доступ. Якщо localStorage недоступний, вхід працює лише до оновлення поточної вкладки.

На Vercel додайте `NEXT_PUBLIC_APP_ACCESS_PASSWORD` у Settings → Environment Variables для потрібних середовищ, потім зробіть новий deploy. Змінна публічна та включається в клієнтську збірку; кожна зміна потребує нової збірки/deploy. Це погоджений тимчасовий механізм для особистого тестування: він обмежує лише UI, API залишається відкритим. Серверної авторизації, cookie та сесій немає. Пароль не передається в URL чи API та не логується.

Gate охоплює всі маршрути перед `AreasProvider` і компонентами сторінок: до перевірки localStorage вони не монтуються й не завантажують дані. SettingsProvider і початкова тема залишаються спільними для екрана входу та застосунку. Прямі URL, query та F5 зберігаються. Під час відкритої модалки навігація виходу недоступна; спочатку закрийте її через наявний механізм discard.

Цільові перевірки: `node --test tests/app-access.test.mjs tests/routine-schedule-versions.test.mjs`. Браузерний сценарій `tests/app-access-browser.mjs` використовує лише тестове значення `APP_ACCESS_TEST_PASSWORD`, яке має збігатися з тестовим env frontend, та мокований API; справжній пароль для тестів не використовуйте. Він перевіряє вхід, сховище, F5/прямі URL, іншу вкладку, відмову localStorage, відсутність запитів до входу, мобільний вигляд і вихід із незбережених налаштувань. Для сценарію без env задайте `MISSING_APP_URL` на окремий frontend без налаштованого пароля.

## Локальний запуск

1. Встановіть залежності: `npm install`.
2. Скопіюйте `.env.example` у `.env.local`. За замовчуванням `NEXT_PUBLIC_API_URL=http://localhost:4000/api`.
3. Запустіть backend. Його CORS має дозволяти адресу frontend (локально `http://localhost:3000`).
4. Запустіть `npm run dev` та відкрийте `http://localhost:3000`.

Після зміни `NEXT_PUBLIC_API_URL` перезапустіть dev-сервер; для production виконайте нову збірку, оскільки Next.js вбудовує публічні змінні у клієнтський код.

## Структура Tasks і Routines

Предметний код Tasks розташований у `src/modules/tasks`: `api` містить API-обгортки, `model` — типи, валідацію та чисту логіку, `hooks` — React hooks, `ui` — компоненти та їхні локальні стилі, `screens` — реалізацію екрана списків. Внутрішній розділ `routines` містить власні `api`, `model`, `hooks`, `ui` та `routines-screen.tsx`. Публічна точка входу екранів — `src/modules/tasks/screens.ts`.

Другий етап відокремлює Areas, Settings, доступ і спільний технічний код. Тонкі обгортки маршрутів — `src/app/page.tsx`, `src/app/routines/page.tsx` і `src/app/settings/page.tsx`. Тести й fixtures залишаються в `tests`.

- `src/entities/areas/api/areas.ts`, `model/{area-types,area-validation,use-areas}`, `ui/{area-select,areas-modal,delete-area-dialog,areas.module.css}` замінюють відповідні файли в `src/lib`, `app/_hooks` і `app/_components`. Публічні точки входу: `public.ts` (типи, валідація, API), `ui.ts` (provider/hook, вибір і керування).
- `src/modules/settings/model/{settings,settings-store,settings-storage,theme,use-settings}` і `ui/{settings-screen,settings.module.css}` замінюють реалізації в `src/lib`, `app/_hooks` і `app/settings`. Точки входу: `preferences.ts` (клієнтський provider/hook і типи), `preferences-runtime.ts` (чисті helpers), `screen.ts` (екран), `theme.ts` (bootstrap для layout).
- `src/application/access/model/app-access.ts` і `ui/{app-access.tsx,app-access.module.css}` замінюють реалізації доступу в `src/lib` та `app/_components`.
- `src/shared/api/api.ts`, `dates/{format-date,zoned-date}.ts`, `lib/format-duration.ts`, `navigation/{history-traversal-guard,use-history-traversal-guard}`, `hooks/use-open-dialog.ts`, `ui/{discard-changes-dialog,zoned-date-time-field}.tsx` замінюють відповідні старі файли. Предметні `DateField`/`DateOptions` залишені в `src/modules/tasks/model/task-date-options.ts`.

Третій етап переносить оболонку до `src/application/shell/app-shell.tsx` як `AppShell`. Активний пункт задається одним `activeItem`: current/today/backlog/archive/routines/settings. Application використовує вузький `src/modules/tasks/routes.ts`: побудова URL розділів Tasks і збереження фільтрів залишаються в Tasks. Routines і Settings мають ті самі URL та query; реєстру модулів немає.

`AppShell` — єдиний власник `AreasModal` та її opener. Він монтується всередині кожного наявного екрана; спільного route layout не додано. Екран передає перевірку переходу та запиту відкриття Areas. Tasks враховує pending, refreshRequired та інші locks навіть без діалогу; зміни розділу залишаються відкладеними до звільнення форми/lock. Routines зберігає modalLock і pending GET редактора; Settings використовує своє dirty-підтвердження та чинний HistoryTraversal blocker. Нових blockers немає.

Areas повідомляє нейтральну `changeRevision` після успішного створення/перейменування/видалення. Tasks і Routines самі завантажують залежні списки й показують помилки/retry на своїх екранах. AreasModal має лише `opener`/`onClose`; контрактів Tasks або імпортів Tasks/Routines в entity немає. Закриття Areas без змін більше не запускає зайвий GET Routines; зміна сфери запускає GET одразу, незалежно від закриття модалки. Невдалий GET не повторює мутацію.

Тимчасові залежності: Settings, Areas, access, AppShell і shared UI ще використовують `src/app/page.module.css`. Екрани модулів знають AppShell як компонент композиції; AppShell знає публічні маршрути Tasks і фіксовані пункти застосунку. HTTP-клієнт зберігає попередні тексти помилок 404/409 зі згадками задач.

Серверний `src/application/providers.tsx` збирає незмінний порядок і межі монтування: HistoryTraversalProvider → SettingsProvider → AppAccessProvider → AreasProvider → сторінки. Root layout залишається серверним. До входу Areas, AppShell і сторінки не монтуються та їхні API-запити не виконуються. CSS-правила та їхній порядок збережені.

Перевірки другого етапу: `npm run build`, `npm run lint`, `npm run typecheck`, `node --test tests/*.test.mjs`, `git diff --check HEAD`. Браузерні сценарії — `tests/app-access-browser.mjs`, `tests/routine-schedule-browser.mjs`, `tests/areas-settings-browser.mjs`; усі запускаються послідовно на тестовій збірці з `NEXT_PUBLIC_API_URL=http://mock.invalid`, тестовим `NEXT_PUBLIC_APP_ACCESS_PASSWORD`, відповідним `APP_ACCESS_TEST_PASSWORD`, `APP_URL` і окремим CDP-профілем. Новий сценарій перевіряє відкриття Areas, чернетки, повернення фокуса, збереження теми/timezone після F5 і query без мутацій API. Для перевірки відсутнього пароля потрібен окремий frontend і `MISSING_APP_URL`/`ACCESS_MISSING_ONLY=1`. Секретні `.env` для тестової збірки не потрібні.

Третій етап додає `tests/shell-routes.test.mjs` для збереження query/фільтрів у публічному контракті маршрутів і `tests/app-shell-browser.mjs` на тому самому CDP та мокованому API. Браузерний сценарій перевіряє мутації Areas й залежні Tasks/Routines, GET-only retry, pending/refreshRequired без діалогів, чернетки/Back/Forward, одного власника Areas, фокус, scroll і 1440/390 light/dark. `CreateTaskModal` явно обробляє Escape перед native cancel: це зберігає dirty/pending checks після history traversal. Фактичні результати й додаткові зміни описані у [звіті третього етапу](FRONTEND_STAGE3_REPORT.md).

## API

- `GET /tasks` — масив повних Task DTO; `GET /tasks?view=today` — підмножина «Сьогодні»; `GET /tasks?view=backlog` — беклог; `GET /tasks?archived=true` — архів.
- `GET /tasks/:id`, `POST /tasks`, `PATCH /tasks/:id` — повний Task із boolean `isToday`, `isBacklog` та nullable `routineOccurrence`, включно з полями ланцюжка виконань. Runtime-валідація вимагає обидва boolean.
- POST вимагає назву, дедлайн і тривалість або початкові підзадачі. PATCH передає лише змінені поля; контекст не входить у body.
- `DELETE /tasks/:id` — видалення задачі.

Список, деталі, POST і PATCH отримують `timezone`, `overdueMode`, `overdueDays` із завантажених налаштувань. Історія, DELETE і маршрути підзадач цих параметрів не отримують. Після запису підзадачі окремий GET батька використовує актуальний контекст; повтор після помилки GET не повторює запис. Повний Task із POST/PATCH оновлює список без додаткового GET, якщо контекст не змінився.

URL: `/` — поточні, `/?view=today` — сьогодні, `/?view=backlog` — беклог, `/?archived=true` — архів. Архів має пріоритет над view; невідомі view означають поточні. API ніколи не отримує archived=true разом із view. Переходи зберігають фільтри й сторонні query-параметри; «Скинути» зберігає розділ. Фільтри, пошук, сортування та зміна теми не завантажують задачі повторно.

«Сьогодні» використовує тільки backend isToday. Після фільтрації задачі поділяються на «До виконання» та «Виконано сьогодні» (DONE), зі збереженням сортування всередині кожної групи. Обидві групи входять до загального лічильника. Повний Task DTO містить `completedAt: string | null` — підтверджений backend момент поточного завершення; frontend його не обчислює. Завершення й повторне відкриття переміщують ту саму картку між групами, якщо isToday залишається true; розгортання підзадач зберігається. Поточні задачі й архів залишаються одним списком.

Спільний механізм оновлює Task-перегляди кнопкою «Оновити список», при поверненні до вкладки та одним таймером до найближчого майбутнього plannedAt/dueAt або наступної півночі в поясі налаштувань чи відомих occurrence. Для DST використовується Temporal, а довгі затримки обмежено максимумом setTimeout. У прихованій вкладці таймер призупинено; повернення завантажує свіжі дані. Немає частого polling або запитів на кожну Task. «Сьогодні» й «Беклог» паралельно читають один базовий список поточних задач, щоб знати межі прихованих задач; успішні мутації актуалізують цей список повним DTO. Якщо базовий GET не вдався, вибраний список доступний, але автоматичні часові межі відомі лише для завантажених задач; інтерфейс пояснює обмеження, ручне оновлення залишається доступним. Вчорашні завершення зникають за новою відповіддю backend. Зміна API-контексту відразу приховує попередній результат; власники відкритих форм тимчасово зберігаються з явним повідомленням про неактуальні картки. Новий контекст після успішного запису оновлюється читанням, без повтору мутації.

«Беклог» показує задачі, які потребують нового плану: без актуального планування чи майбутнього дедлайну. Увесь відбір виконує backend; frontend не відтворює календарних правил і не обчислює isBacklog. Після POST/PATCH або GET батька після мутації підзадачі isBacklog=true додає/залишає картку, false прибирає. Видалення прибирає картку після успіху. Поза беклогом створена задача отримує повідомлення про доступність у «Поточних задачах», як у «Сьогодні». Чотири групи підсумку рахуються до frontend-фільтрів, «Знайдено N із M» — після них; групи «Виконано сьогодні» тут немає. Порожній беклог і відсутність збігів мають окремі стани. Повернення з Routines враховує спільну інвалідацію після генерації.

Перевірки: `npm run lint`, `npm run typecheck`, `npm run build`.

Ручний сценарій беклогу (лише на мокованому API): відкрийте `/?view=backlog&third=keep`, перезавантажте сторінку, перейдіть у «Сьогодні» й назад через Back/Forward. Поєднайте пошук, статус, пріоритет, сферу й сортування; перевірте лічильник та «Скинути» зі збереженням view/third. Переплануйте задачу й поверніть DTO з isBacklog=false; перевірте зникнення. Повторіть для IN_PROGRESS/DONE/CANCELED та збереження PAUSED/POSTPONED із isBacklog=true. Змініть підзадачу, зімітуйте помилку GET батька й повторіть тільки GET. Перевірте створення поза беклогом, архівування й видалення, розгортання за ID та незбережені форми при переходах. Для часу додайте у базовий список приховану задачу з близькою майбутньою датою, змініть мокований backend-відбір і дочекайтеся одного оновлення; повторіть із прихованою вкладкою та occurrence в іншому поясі. Помилка базового GET має залишити беклог доступним із поясненням. Перевірте запізнілу відповідь старого розділу, повернення з Routines, 1440/390 px, light/dark, клавіатурний фокус і прокручування.

## Компонування списку задач

Підсумок над фільтрами рахує весь завантажений список поточного розділу: TODO, IN_PROGRESS, неактивні (CANCELED/PAUSED/POSTPONED/SKIPPED) та DONE. Він не залежить від пошуку, фільтрів і підзадач та не виконує API-запитів. Розкладка неактивних доступна через клавіатурне розкриття. Під час завантаження або помилки без даних замість достовірних нулів показується повідомлення.

На широкому екрані заввишки від 48rem каркас задач займає viewport, панель керування залишається над областю прокручування, обидві групи «Сьогодні» прокручуються разом. Навігація має власне прокручування, якщо не вміщається. Для вузьких/низьких viewport використовується звичайне прокручування документа, а на мобільному фільтри можна розгорнути кнопкою з кількістю активних умов. Згортання не змінює URL. `/settings` зберігає звичайне компонування.

## Пропуск створеного виконання Routine

`TaskStatus` містить `SKIPPED` («Пропущено»); окремі `SubtaskStatus` і `SUBTASK_STATUSES` залишають попередні шість статусів. Runtime-валідація вимагає nullable `skipNote`, `skippedAt` у повному Task DTO й відхиляє SKIPPED у підзадачах. Чинні summary, isToday/isBacklog, completedAt і всі поля occurrence збережені; occurrence також містить `basisType: COMPLETED | SKIPPED | null` і `basisAt: string | null`. Дата пропуску береться з API, навіть якщо через непевну історію вона null.

Неархівована Routine Task має швидку дію «Пропустити». Вона й вибір SKIPPED у статусах відкривають один діалог із назвою, поясненням незмінності підзадач та необов’язковою причиною. Порожнє введення надсилається як null; непорожнє обрізається через trim та обмежується 2000 символами після trim. Є блокування одного батька, синхронний захист повторного submit, збереження причини при помилці PATCH, блокування закриття під час запиту, Escape/Tab/Shift+Tab, повернення фокуса й чинні discard/history/beforeunload guards для чернетки. Автоматичного повтору PATCH немає.

Звичайні Task та підзадачі не мають SKIPPED у керуванні статусами. Архівована Routine Task підтримує статус через чинний Task PATCH, без швидкої дії. Для вже пропущеної задачі checkbox швидкого завершення прихований, повторний вибір SKIPPED нічого не записує. Повернення через «До виконання» надсилає тільки TODO; очищення skipNote/skippedAt і синхронізацію дітей визначає backend. Інші переходи зберігаються. Повний PATCH DTO актуалізує картку та backend-відбір розділу; розгортання лишається за ID. Пропуск не змінює підзадачі локально й не генерує наступне виконання.

У деталях показуються «Пропущено» зі skippedAt та непорожня причина. Історія перекладає SKIPPED і показує зміни/очищення skipNote без текстового null. SKIPPED входить до «Неактивних», її розкладки й відсотків, не додається до DONE. Поточний список та архів зберігають пропущені задачі; «Сьогодні» й «Беклог» застосовують isToday/isBacklog із відповіді.

AFTER_COMPLETION може продовжуватися після завершення або пропуску. Підстава в occurrence та generation-preview відображається через basisType/basisAt: «завершення» чи «пропуск» попереднього виконання. Сумісне basisCompletedAt збережено й для SKIPPED може бути null. Preview без контексту результату й далі показує лише перше виконання; фактичний кандидат перевіряється через generation-preview. Ручна генерація залишається явною: алгоритм, planning, ідемпотентність і точний повтор payload не змінено. За ввімкненої автоматизації наступника також може створити серверна перевірка.

Ручна перевірка на моках: відкрийте Routine Task із підзадачами та звичайну Task. Перевірте доступність пропуску лише для першої; пропустіть із причиною та без неї. Зімітуйте помилку й затримку PATCH: причина збережена, подвійне підтвердження дає один запит, закриття заблоковане. Перевірте незмінні підзадачі, відсутній checkbox, TODO і очищені сервером skipNote/skippedAt. Повторіть у «Сьогодні» й «Беклозі», перевірте зникнення за DTO, URL-фільтр SKIPPED, «Неактивні», деталі й історію. Перевірте basisType=SKIPPED з basisCompletedAt=null у Task і generation-preview, клавіатуру, discard/history guard та 390 px. Жоден пропуск не має викликати generate POST.

## Особисті налаштування

Екран `/settings` доступний із меню. Налаштування застосовуються після натискання «Зберегти», без облікового запису. Адаптер `settings-storage.ts` зберігає перевірені поля та `version: 1` у ключі `personal-platform.settings`. Якщо localStorage недоступний, provider зберігає зміни лише в пам’яті поточної вкладки. Події `storage` оновлюють інші вкладки без повторного запису; незбережена форма пропонує завантажити зовнішні значення або зберегти власні.

Часовий пояс за замовчуванням береться з браузера, резервний — UTC. Відображення дат використовує обраний пояс. Відкрита форма фіксує його до закриття, щоб зовнішня зміна налаштувань не переосмислила чернетку. Спільні helpers на `@js-temporal/polyfill` відхиляють неіснуючі години DST та вимагають явного вибору UTC-зсуву для повторених годин. API отримує UTC; незмінені дати не включаються в PATCH (для перенесення зберігається точне початкове `plannedAt`).

Теми використовують спільні CSS-змінні. Системна тема реагує на `prefers-color-scheme`; збережена світла або темна палітра встановлюється блокувальним скриптом у head до відображення сторінки. Він змінює CSSOM, зберігаючи DOM однаковим для SSR і hydration.

Параметри прострочення застосовуються до перегляду «Сьогодні» на backend: limited додає N попередніх календарних днів, none залишає тільки сьогодні, all додає всі попередні дні. Локальні дати й час occurrence відображаються у його календарі, окремо від особистого планування та дедлайну. Беклог передає той самий контекст, хоча його відбір від параметрів «Сьогодні» не залежить.

## Повторювані задачі

`/routines` показує список шаблонів, створення, редагування, деталі, preview розкладу, паузу/відновлення та явну генерацію задач. Доступне явне видалення шаблону з підтвердженням. «Активний» означає лише відсутність паузи. Шаблони підзадач мають власний порядок і тривалість; вони не є Task/Subtask та не мають статусів виконання.

Окремі модулі `routine-types.ts`, `routine-validation.ts`, `routine-format.ts`, `routines.ts` підтримують schedule v1 (DAILY, WEEKLY DAYS/WINDOW, MONTHLY DAY/WINDOW/LAST_DAY, AFTER_COMPLETION) та NEVER/UNTIL_DATE/COUNT. Routines не отримують today-контекст: календар і час належать timezone шаблону.

Кнопка «Нове повторення» відкриває модалку з основними полями та редактором шаблонів підзадач ліворуч і розкладом праворуч; на мобільному колонки складаються вертикально. Початкові timezone та дата беруться із завантажених налаштувань і локального сьогодні в цьому поясі. Зміна timezone не переосмислює введену дату. Політика короткого місяця задається явно для DAY/WINDOW; COUNT означає заплановані виконання, а не кількість DONE.

`create-routine-input.ts` перевіряє поля, локальні дати, інтервали й перехресні межі, обрізає пробіли та явно складає одну discriminated-union гілку schedule v1. При підзадачах оцінка показує суму лише для читання; після видалення всіх рядків повертається попередня ручна оцінка. POST надсилає лише назви й числові тривалості підзадач, без локальних ID або статусів. Переповнення суми блокує збереження.

POST `/routines` використовує спільний API-клієнт і runtime-валідацію Routine. Синхронний guard захищає від подвійного submit; під час запиту редагування й закриття заблоковані. Помилки залишають повну чернетку, відомі validation paths прив’язуються до полів. Видалена сфера потребує ручного оновлення довідника/вибору та повторного POST користувачем. Невдале завантаження Areas не блокує створення без сфери. Успішний DTO одразу додається до списку без повторного GET із повідомленням «Шаблон повторення створено». Збереження шаблону не запускає generation або preview із браузера. Якщо автоматизацію ввімкнено, задачі може створити окрема серверна перевірка.

Створення й редагування використовують одну `RoutineFormModal`, спільні поля, валідацію та редактор підзадач. Календарний редактор у цій формі доступний лише для створення. Чернетки захищені наявними `DiscardChangesDialog`, `useHistoryTraversalGuard` і стандартним `beforeunload`. Escape/«Скасувати» пропонують відкинути зміни; під час POST/PATCH редагування, закриття й повторний submit заблоковані. Після закриття фокус повертається до кнопки відкриття. Спільна форма Task та її поведінка не змінювалися.

Дія «Редагувати» спершу читає актуальний GET `/routines/:id`; лише після успіху відкривається форма. Завантажений snapshot фіксується до закриття, тому фонові оновлення не перезаписують чернетку. `edit-routine-input.ts` нормалізує текст/числа та порівнює структури без залежності від порядку ключів об’єктів. Без змін PATCH не виконується. PATCH містить лише змінені назву, опис, сферу, пріоритет, тривалість і шаблони підзадач; timezone/startDate/schedule/endCondition виключені з типу й побудови payload. Очищення сфери передає `areaId: null`; підзадачі — впорядкованим масивом лише з назв і тривалостей. При видаленні всіх підзадач передаються `subtasks: []` та власна тривалість.

Календарні зміни виконуються через незмінні версії розкладу, також до першої генерації. Застарілий спеціальний 409/reset для повної заборони зміни календаря після генерації видалено. Уже створені задачі не переписуються. Після успішного звичайного PATCH список оновлюється повним DTO без обов’язкового GET; попередній запит списку скасовується, щоб не перезаписати результат.

Preview виконує тільки GET з `from`, `to`, `limit=100`: початково сьогодні у timezone Routine та наступні 30 днів. Діапазон обмежений 366 днями включно. Зміна полів не надсилає запиту до натискання кнопки. Локальні дати відображаються без перетворення на timestamps; календар повторень обчислює backend. Невідомі diagnostics/limitations залишаються валідними даними й отримують нейтральне пояснення. AFTER_COMPLETION не надсилає припущень про завершення або номер виконання; preview не є історією чи списком створених задач.

Пауза надсилає лише PATCH `{ paused: boolean }`, блокує повторні записи відповідного шаблону та оновлює список/відкриті деталі повним DTO. Старий preview скидається й повторно читається для останнього застосованого діапазону. Помилка preview після успішної паузи відображається окремо; повторюється лише GET. Уже створені задачі не змінюються. Запізнілі відповіді деталей і preview відкидаються через AbortSignal та перевірку поточного ресурсу.

Ручна перевірка на мокованому API: відкрити всі види розкладу, перевірити вікна й політики короткого місяця; preview з DST/невідомими обмеженнями/truncated/404; паузу й відновлення, повторні натискання та успішний PATCH із невдалим preview; Escape, Tab/Shift+Tab і повернення фокуса. Повторити на 1440/390 px у light/dark та перейти до інших розділів.

Створення на моках: масаж кожні 2 дні до дати, понеділок/четвер, вікно субота–неділя, місячне вікно 15–23, останній день місяця, AFTER_COMPLETION через 90 днів; NEVER/UNTIL_DATE/COUNT. Перевірити перемикання зі збереженням прихованих чернеток, підзадачі/переповнення/повернення ручної оцінки, 400/404 зі збереженням полів, подвійний submit, discard і Back/Forward. У Network має бути один POST на збереження й жодного generation-запиту.

Редагування на моках: без змін — без PATCH; лише назва — лише `title`; очищення сфери; підзадачі та перехід до ручної тривалості. Перевірити concurrency 409, 400/404, повторний submit та запізнілий GET. Повторити створення, preview і pause/resume; на широкому/390 px перевірити прокручування, Tab/Shift+Tab, Escape, discard і обидві теми.

### Версії розкладу Routine

Контракт звірено з README, schemas, routes, mapper, versions service та resolver сусіднього backend. `getRoutineScheduleVersions` і `createRoutineScheduleVersion` використовують спільний API-клієнт, AbortSignal і runtime-валідацію повного DTO. GET `/routines/:id/schedule-versions` завантажується лише у відкритих деталях; картки не запитують версії. Завантаження, помилка й повтор GET незалежні від деталей Routine та preview. Версії відображаються за number ASC із номером, календарною effectiveDate, effectiveTimezone, timezone, повторенням, часом і завершенням. Чинна версія визначається за effectiveAt; статус оновлюється кожні 30 секунд. Календарні поля самої Routine є mirror останньої збереженої версії, включно з майбутньою.

«Деталі → Змінити розклад» відкриває широку форму зі спільним `RoutineScheduleEditor` і `parseRoutineRule`. Основа чернетки явно названа: остання збережена версія. POST містить усі п’ять полів: `{ effectiveDate, timezone, startDate, schedule, endCondition }`. effectiveDate — початок дня в незмінному effectiveTimezone першої версії; вона не перетворюється через UTC для відображення. Мінімум — наступний локальний день і строго пізніше останньої effectiveDate/effectiveAt; точну перевірку часу під блокуванням повторює сервер. startDate задає прив’язку повторення окремо від межі дії. Ліміт — 100 версій; calendar ↔ AFTER_COMPLETION недоступний, startDate AFTER_COMPLETION заблокований. COUNT є спільним лімітом через версії без скидання; сервер перевіряє його проти всіх матеріалізованих виконань.

Перед POST потрібні checkbox підтвердження й явне натискання «Створити версію». Показується: «Новий розклад діятиме з вибраної дати. Уже створені задачі, включно з майбутніми, залишаться без змін». Є синхронне блокування подвійного submit, закриття під час запиту, фокус, Tab/Shift+Tab, Escape, discard/history/beforeunload. 400/409 зберігають чернетку. Валідний успіх замінює форму окремою компактною `RoutineResultModal`: номер версії, effectiveDate у календарному форматі та пояснення незмінності вже створених задач. Окремо оновлюються версії та Routine; помилка наступного GET показується в результаті разом з успіхом і кнопкою повтору лише GET. Кнопка «Закрити» та Escape повертають фокус на «Змінити розклад» без запитів і discard. При втраті відповіді, 5xx або невалідному успішному DTO початкова форма залишається відкритою: доступна перевірка версій через GET, автоматичного чи сліпого повтору POST немає.

Поки відкрито форму зміни або результат, simulation preview приховано зі збереженням змонтованого компонента; закриття результату не запускає GET. Подія зміни розкладу інвалідує simulation preview та generation-preview, залишаючи чернетки planning до нового GET. Після GET зберігаються лише чинні нові occurrenceKey; зниклі/existing вилучаються з явним повідомленням. Планування та DST перевіряються у timezone кожного виконання, бо один діапазон може містити різні версії й пояси. conflicts у preview/generation-preview/generate перевіряються й відображаються окремо: виконання пропущене через перетин зі збереженою задачею або ранішим кандидатом. Вони не додаються до createdCount. Existing та точний явний повтор попереднього generation payload при невизначеному результаті збережені. Жодна зміна розкладу не викликає Task PATCH або generate POST.

Автоматичні моки без додаткових залежностей: `node --test tests/routine-schedule-versions.test.mjs`. Браузерні моки: запустіть frontend та окремий Chromium/Edge з `--remote-debugging-port=9223` і тимчасовим `--user-data-dir`, потім `node tests/routine-schedule-browser.mjs` (за потреби `APP_URL`/`CDP_URL`). Скрипт перехоплює API до мережі й блокує сторонні запити; використовує лише тестові fixtures. Перевіряє версії, незалежний retry, повний POST, 400/409, подвійне підтвердження, невизначені результати, успіх із помилкою GET, PATCH, conflicts/planning/exact retry, Escape/чернетки й 1440/390 light/dark. Скріншоти пишуться в системний tmp. Загальні перевірки: `npm run build`, `npm run lint`, `npm run typecheck`, `git diff --check`.

Короткий ручний сценарій на моках: відкрийте деталі з попередньою, чинною й майбутньою версіями; перевірте основу нової форми та мінімальну дату. Змініть час, натисніть Escape, продовжте редагування, підтвердьте й збережіть двічі при затриманій відповіді. Після успіху зімітуйте помилку GET й повторіть лише GET. Окремо змоделюйте втрату POST-відповіді та перевірте версії. Відкрийте генерацію, оновіть кандидати зі зміненими ключами й conflicts: старий planning не надсилається, existing майбутні задачі зберігаються, конфлікти не рахуються створеними. Перевірте звичайне редагування, створення, pause/resume, видалення та SKIPPED; повторіть клавіатуру й обидві теми на 390 px.

### Видалення Routine

Компактна дія «Видалити» у картці відкриває окремий діалог «Видалити повторення?» з назвою шаблону та поясненням наслідків. Початковий фокус — «Скасувати». Діалог не відкривається поверх деталей, редактора або генерації. Тільки явне підтвердження викликає DELETE `/routines/:id` через спільний `requestDelete`: успішний 204 обробляється без читання JSON, body та query не передаються.

Синхронний guard і спільне блокування Routine захищають від повторного підтвердження та конфліктних мутацій. Під час запиту закриття, Escape і переходи назад/уперед заблоковані. Збережені Tab/Shift+Tab, блокування фону, внутрішнє прокручування та обидві теми. Після скасування фокус повертається на ініціатор; після видалення — на заголовок списку, якщо кнопки вже немає.

Після 204 шаблон прибирається з локального списку без обов’язкового GET, діалог закривається й показується повідомлення. Запізнілий GET скасовується та перевіряється за ревізією, тому не може повернути видалений шаблон. Уже створені Tasks, їхня історія й відбір current/today не змінюються. Відновлення шаблону через інтерфейс недоступне.

404 означає, що шаблон уже недоступний: список синхронізується, діалог пояснює стан, повторне підтвердження недоступне, закриття дозволене. Інші помилки залишають діалог відкритим із безпечним повідомленням. Мережева помилка або 5xx не доводять, що видалення не відбулося. Дія «Перевірити актуальний список» робить лише GET `/routines`, без повторного DELETE: недоступний шаблон зникає зі списку, наявний потребує нового явного підтвердження. Помилка перевірки показується окремо. Автоматичних повторів DELETE немає.

Ручна перевірка на моках: відкрити й скасувати без DELETE; підтвердити двічі — один запит, 204 без JSON. Перевірити 404, 409, 500 і втрату відповіді, потім GET-перевірку без повторного видалення. Затримати старий GET, видалити останню Routine та повернути стару відповідь: список лишається порожнім. Перевірити фокус після скасування/видалення, Escape, Tab/Shift+Tab, 390 px, light/dark і наявні створення, редагування, preview, pause/resume та генерацію. Усі мутації під час перевірок — лише на мокованому API.

### Автоматичне створення задач із Routine

Контракт звірено з README, Routine DTO/mapper, POST/PATCH-схемами та runner сусіднього backend. Routine містить обов’язкові у відповіді `autoGenerate: boolean` і `generationHorizonDays: integer` (1–30). Defaults POST та форми — `false` і `7`. Обидва поля належать Routine, змінюються звичайним PATCH і не входять до версій розкладу. Звичайне редагування надсилає лише фактично змінені поля, включно з окремим перемиканням автоматизації без повторного надсилання горизонту.

У створенні та редагуванні є блок «Автоматичне створення задач». Вимкнення checkbox не скидає введений горизонт. Для AFTER_COMPLETION поле приховане, значення зберігається у чернетці та payload. Календарний горизонт включає сьогодні: 7 — сьогодні та наступні 6 днів у timezone розкладу. Після простою календарні виконання створюються від поточного дня, активне багатоденне вікно включається повністю. AFTER_COMPLETION створює максимум одного наступника після завершення або пропуску під час найближчої перевірки сервера, незалежно від горизонту. Вимкнення або зменшення горизонту не змінює створені Tasks; пауза Routine призупиняє і автоматичне створення.

Список показує компактний увімкнений стан, деталі — також «Вимкнено» та пояснення паузи. DTO повідомляє лише налаштування: глобальне ввімкнення runner контролюється backend. Немає відліку, вигаданого часу проходу, polling чи прихованих POST. Успішне збереження з валідним POST/PATCH DTO оновлює Routine у списку та деталях і повідомляє лише про збереження шаблону. Воно не викликає generate та не підтверджує створення Tasks. Ручна генерація, оновлення Tasks при навігації та ручна кнопка оновлення збережені.

Перевірки без додаткових залежностей: `node --test tests/routine-schedule-versions.test.mjs` охоплює defaults, 1/30, відхилення 0/31/дробів, строгий DTO, мінімальний PATCH, AFTER_COMPLETION, паузу та помилки/невалідні відповіді API. Наявний `tests/routine-schedule-browser.mjs` перевіряє автоматизацію на перехопленому мокованому API разом із регресією версій, ручної генерації, planning, результатних модалок, створення та видалення. Запуск: frontend із тестовим `NEXT_PUBLIC_API_URL`, окремий headless Chromium/Edge із `--remote-debugging-port=9223` і тимчасовим профілем, потім `APP_URL=http://127.0.0.1:3000 node tests/routine-schedule-browser.mjs`. Усі API-запити браузера перехоплюються; реальні дані не змінюються.

Ручний сценарій на моках: створити шаблон із defaults; змінити горизонт на 30, вимкнути/увімкнути checkbox і перевірити збереження значення; перемкнути AFTER_COMPLETION і назад. Перевірити 1/30 та помилки 0/31/дробів біля поля, discard/продовження чернетки й фокус. Зберегти автоматизацію через мінімальний PATCH, перевірити список і деталі, вимкнення та паузу; переконатися у відсутності `/generate` і POST версії розкладу. Змоделювати 400 та невалідну успішну відповідь: чернетка залишається. Повторити на 1440/390 px, light/dark і клавіатурою; окремо виконати явну ручну генерацію та перейти до Tasks/оновити список.

### Явне створення задач із Routine

Картка має дію «Створити задачі» з окремим діалогом підтвердження. Для paused-шаблону кнопка недоступна з поясненням необхідності відновлення. Початковий діапазон — сьогодні та наступні 30 календарних днів у timezone Routine. Локальні дати перевіряються за тим самим контрактом, що й preview: від 0001 до 9999 року, `from <= to`, максимум 366 днів включно. Вікно, яке перетинає діапазон, створюється цілком. Ліміт — 100 нових задач за запит; AFTER_COMPLETION створює максимум одне нове виконання за запуск, а наступника визначає backend за фактичним завершенням.

Кнопка «Показати виконання» викликає GET `/routines/:id/generation-preview?from=...&to=...` зі спільним HTTP-клієнтом, AbortSignal та runtime-валідацією. Це фактичні кандидати resolver, а не simulation preview розкладу. Для AFTER_COMPLETION backend використовує збережені завершення; клієнт не передає completedAt і не обчислює наступника. GET не запускається автоматично при відкритті чи введенні дат. Немає запитів окремих existing Tasks.

Для нових виконань доступне необов’язкове поле «Заплановано», початково порожнє. Existing не мають поля: особистий план можна змінити в самій задачі. Одноденне виконання має компактне поле часу, а дата береться з дати виконання. Для вікна доступні дата (початково startDate) і час; без часу planning не надсилається. Введення відбувається у timezone конкретного виконання через спільні timezone/DST helpers: неіснуючий DST-час відхиляється, неоднозначний потребує явного вибору зсуву. У POST час передається як ISO UTC. План поза початковим вікном дозволений і має неблокувальне пояснення. localTime/instant розкладу не підставляються у план автоматично.

Тільки явне підтвердження викликає POST `/routines/:id/generate` з body `{ from, to, planning?: [{ occurrenceKey, plannedAt }] }`. До planning потрапляють лише заповнені валідні нові виконання: ключ береться з відповіді, очищені поля пропускаються. Можна запланувати частину кандидатів або залишити всі без плану. Ліміт planning — 100 для календарного режиму й 1 для AFTER_COMPLETION. Today-контекст, query, limit, completedAt і номер виконання не передаються. Синхронний guard блокує подвійний submit; під час POST поля, закриття й конфліктні дії заблоковані. Наявні discard-dialog, history guard і beforeunload захищають дати та всі поля планування.

Генерація доступна лише після успішного GET поточного діапазону. Зміна діапазону скасовує попередній запит і робить список неактуальним; запізнілі відповіді ігноруються. Помилка GET зберігає чернетку, повтор виконує лише GET. Після оновлення зберігаються введення тільки для ключів, які залишились новими. Зниклі або existing заплановані рядки вилучаються з явним повідомленням; жоден GET не запускає POST. Помилка застарілого planning пояснює необхідність оновити виконання.

Runtime-валідація generate перевіряє посилання, лічильники й відповідність діапазону та Routine. Після успішного POST із валідним DTO форма закривається без discard, також при 0/0 та після успішного точного повтору. Відкривається окрема компактна `RoutineResultModal` із createdCount, existingCount і conflicts. Початковий фокус — «Закрити»; Tab/Shift+Tab залишаються в модалці. Кнопка та Escape закривають результат без запитів і повертають фокус на кнопку початку генерації. На сторінці Routines також зберігаються лічильники та розкривний блок conflicts останнього успішного результату. Existing не відкриваються автоматично: серед них можуть бути м’яко видалені задачі. Новий запуск потребує відкриття форми, нового generation-preview та явного натискання. Помилка або невизначений результат залишають початкову форму відкритою з чернеткою й точним надісланим payload.

Помилки 400/404/409 зберігають введення; пауза, очікування DONE, DST, історія й ліміт мають різні пояснення. Для втрати відповіді, 5xx або невалідної успішної відповіді показується невизначений результат: запит міг виконатися. Зберігається точний серіалізований payload із planning; «Повторити точний запит» надсилає його за явною дією незалежно від новіших змін чернетки. Автоматичного POST немає. Повтор не дублює й не переплановує existing. Новий запит із поточної чернетки потребує завершення точного повтору та оновлення кандидатів.

Окрема дія «Перейти до поточних задач» відкриває `/`. Після успіху або невизначеного результату `task-list-invalidation.ts` позначає Tasks для повторного GET, включно зі збереженим станом маршруту. Generate-відповідь не вставляється у Tasks вручну: повних DTO в ній немає. Current/today відбір не змінюється. Допоміжний GET після генерації не запускається, тому його помилка не може повторити запис.

Ручна перевірка на моках: відкрити діалог без запитів, завантажити три нові кандидати й existing, запланувати два з трьох та перевірити UTC payload і відсутність поля existing. Очистити поле, перевірити порожній planning, DST gap/fold, AFTER_COMPLETION, зміну діапазону й запізнілий GET. При повторному GET перевести ключ в existing або прибрати його та перевірити повідомлення. Змоделювати GET/POST-помилки й втрату відповіді: діалог відкритий, чернетка збережена, точний повтор має ідентичний body навіть після зміни діапазону та введення. Подвійне натискання дає один POST. Валідний успіх закриває діалог без discard, повертає фокус і показує лічильники на сторінці; розгорнути conflicts та перевірити пояснення. Повторити успіх із 0/0 і точний повтор за наявності новіших ненадісланих правок. Перейти до Tasks та перевірити актуальний список. Повторити клавіатуру, discard, прокручування довгого списку, 390 px, light/dark і наявні дії Routines.
